# Pizza v0.2.0 — Hotbar Menu Item, New Catalog Items, Title Colour Fix

**Date:** 2026-07-24
**Status:** Approved (design)
**Plugin:** `org.xpfarm:pizza` — bumps `0.1.0` → `0.2.0`
**Predecessor spec:** `docs/superpowers/specs/2026-07-22-pizza-menu-design.md`

## Context

Pizza v0.1.0 shipped and runs on `play.xpfarm.org`: `/pizza` (aliases `/menu`, `/order`) opens a
Cumulus form for Bedrock players and a chest GUI for Java players, whose buttons dispatch allowlisted
commands from other xpfarm plugins. The whole menu is config data; a fail-closed `command-allowlist`
keeps a config typo from reaching a destructive command.

This increment adds three things, in descending order of design surface:

- **A. A physical hotbar menu item** — so a young Bedrock player never has to type `/pizza`. This is
  the only part with real design decisions and is the bulk of this document.
- **B. Three new catalog items** — Agua de Florida, Electric Furnace, Llama Companion. A pure config
  edit: three buttons and three allowlist roots.
- **C. A colour-code bug fix** — the menu title's `&6` leaks its legacy code into the rendered title
  (a literal `&6` on Java, a stray glyph on Bedrock — the "funky symbol" reported from a device).

Because A is a material feature, v0.2.0 re-enters the plugin lifecycle (plan → dev → release), and
the client play-test already owed for v0.1.0 folds into this release's play-test.

## Part A — Physical hotbar menu item

### Behaviour: self-healing

The item is **self-healing** — a lost item comes back on its own, and it cannot be thrown away. Four
event hooks realise this, and together they guarantee **exactly one** menu item exists per eligible
player at all times:

1. **Give on join.** `PlayerJoinEvent`: if the feature is enabled, the player has `pizza.use`, and no
   tagged item is anywhere in their inventory, give exactly one — placed in the configured hotbar
   `slot` if that slot is empty, otherwise added to the first free inventory slot.
2. **Right-click to open.** `PlayerInteractEvent` (right-click air or block, **main hand only**,
   holding a tagged item): cancel the event and call `MenuService.open(player, "main")`.
3. **Can't drop.** `PlayerDropItemEvent` on a tagged item: cancelled.
4. **Survives death.** `PlayerDeathEvent`: tagged items are removed from `getDrops()` (no litter, no
   loss). `PlayerRespawnEvent`: if the player still lacks one, give it (one tick later, after respawn
   inventory settles).

### Identity: a persistent tag, not the material or name

Every check keys off a **persistent-data tag**, `NamespacedKey(plugin, "menu_item")` set to a byte
`1` on the item's `PersistentDataContainer` — never the material or display name. A child renaming
the item in an anvil, or another plugin handing out a pumpkin pie, can therefore neither break
detection nor forge a second opener. `isMenuItem(ItemStack)` reads that tag and nothing else.

### Configuration

A new `menu-item` block, entirely optional and off-switchable:

```yaml
menu-item:
  enabled: true
  material: pumpkin_pie   # any valid item material
  name: '&6Pizza Menu'    # legacy & colour codes honoured
  slot: 8                 # preferred hotbar slot, 0–8
```

Parsed into an immutable `MenuItemSpec` value with **fail-safe** validation — a bad config disables
the feature rather than crashing `onEnable`:

- `enabled` — boolean, default `true`.
- `material` — resolved via `Material.matchMaterial`; if it does not resolve or is not an item
  (`Material.isItem()` is false), log a warning and treat the whole feature as disabled.
- `name` — string; blank falls back to a built-in default (`"Pizza Menu"`).
- `slot` — integer 0–8 (the hotbar); out of range logs a warning and defaults to `8`.

`MenuItemSpec` becomes a field on `PizzaConfig`, so `/pizza reload` refreshes it exactly like the rest
of the config: the listener reads `menuService.config().menuItem()` per event and a reload takes
effect on the next join or interaction without a restart.

### New unit

One new package, `org.xpfarm.pizza.menuitem`:

- **`MenuItemSpec`** — immutable record (`enabled`, `material`, `name`, `slot`). Pure; validated at
  parse time. Unit-testable without a server.
- **`MenuItemService`** — builds the tagged `ItemStack`, detects the tag (`isMenuItem`), and answers
  "does this player already have one?" (`hasMenuItem`). Depends on Bukkit (`ItemStack`/PDC) so its
  behaviour is play-test-verified rather than unit-tested; the risky *inputs* it consumes (material,
  slot) are validated upstream in the pure `MenuItemSpec`.
- **`MenuItemListener`** — `Listener` wiring the four hooks above to `MenuItemService` and
  `MenuService`. Reads its spec from `menuService.config().menuItem()` so it is reload-correct.

`PizzaPlugin.onEnable` constructs the service with a `NamespacedKey(this, "menu_item")` and registers
the listener. Nothing here imports `org.geysermc.*`; opening the menu goes through `MenuService`,
which already routes Bedrock→form / Java→chest.

### Why cancelling the interact is sufficient

Pumpkin pie is edible, so an uncancelled right-click would eat it. Cancelling `PlayerInteractEvent`
before the vanilla interaction resolves prevents both eating and block placement — no separate
`PlayerItemConsumeEvent` handler is needed. Restricting to `EquipmentSlot.HAND` prevents the
double-fire Bukkit raises for main- and off-hand on a single right-click.

## Part B — New catalog items (config only)

Three buttons appended to the existing `catalog` menu, each `run-as: console` with a per-item
cooldown, plus three roots added to `command-allowlist`. No code changes.

| Label | Dispatch string | New allowlist root | Notes |
|---|---|---|---|
| Agua de Florida | `aguadeflorida give %player%` | `aguadeflorida` | single custom item; `give` covers it |
| Electric Furnace | `electricfurnace give %player%` | `electricfurnace` | gives the machine item; `alloy` subcommand omitted (can't target a player) |
| Llama Companion | `llama give %player%` | `llama` | give lives on the `llama` command, not `ollama`; console dispatch satisfies both `ollama.llama.use` and `ollama.llama.give` |

All three give-actions are op-gated, so console dispatch (as with the existing catalog buttons)
satisfies their permissions. Each remains unreachable unless its root is in the allowlist — the same
fail-closed rule as every other button.

## Part C — Title colour-code fix

### Root cause

Legacy `&` colour codes are never translated for rendered **menu** text. `menu.title()` is
`'&6Pizza Menu'`; `ChestRenderer.titleOf` wraps it in `Component.text(...)` (literal, so Java shows a
literal `&6`), and `BedrockRenderer.open` passes it straight into the Cumulus form (Bedrock renders
the leftover code as a stray glyph — the reported "funky symbol"). Chat **messages** are already
correct — `MenuService.sendMessage` deserializes with `LegacyComponentSerializer.legacyAmpersand()`.
The defect is confined to the renderers' title, content, and button labels.

### Fix

A small shared helper, `org.xpfarm.pizza.render.MenuText`, with two pure methods:

- `static Component java(String legacy)` — `LegacyComponentSerializer.legacyAmpersand().deserialize`,
  the pattern already proven in `MenuService`. `&6` becomes real gold.
- `static String bedrock(String legacy)` — `ChatColor.translateAlternateColorCodes('&', legacy)`,
  yielding `§`-prefixed codes that Bedrock form fields honour, so the title renders gold there too.

Both null/blank-safe (return an empty/hidden result the caller can fall back from, preserving the
existing "blank title falls back to `menu.id()`" behaviour).

- `ChestRenderer` — title, button display names, and any content use `MenuText.java(...)`.
- `BedrockRenderer` — `title`, `content`, and each `button(label)` use `MenuText.bedrock(...)`.

**Play-test dependency.** If the play-test shows Bedrock form *titles* render `§` codes literally
(some clients honour `§` only in content, not the title bar), the `bedrock` helper switches from
translate to **strip** (`ChatColor.stripColor(translate(...))`) — a one-line change isolated to the
helper. The translate path is the primary; strip is the documented fallback.

## Testing

**Unit tests** (server-less, added to the existing suite):

- `MenuItemSpec` parsing: default `enabled`; invalid/blank material → feature disabled + logged;
  non-item material → disabled; blank name → default; slot out of 0–8 → defaults to 8 + logged.
- `MenuText.java` on `'&6Pizza Menu'` → a `Component` coloured gold with content `Pizza Menu` and no
  literal `&`; `MenuText.bedrock` → `'§6Pizza Menu'`; both handle null, blank, and code-free input.
- Config parsing of the three new `catalog` buttons and allowlist roots (dispatch strings, cooldowns).

**Client play-test** (live server — the UX that no headless test can reach, owed since v0.1.0 and now
covering v0.2.0):

- Menu item is given on join, sits in slot 8, and opens the menu on right-click — Bedrock and Java.
- Item cannot be dropped; survives death; a lost item is restored on next join/respawn.
- Menu title renders gold with **no funky symbol** on a Bedrock device (confirms Part C's translate
  path, or triggers the strip fallback).
- The three new catalog buttons each give their item with the configured cooldown.
