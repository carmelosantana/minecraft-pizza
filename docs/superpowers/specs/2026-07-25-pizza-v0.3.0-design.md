# Pizza v0.3.0 — Config Self-Refresh & Consent-Gated Curse

**Date:** 2026-07-25
**Status:** Approved (design)
**Plugin:** `org.xpfarm:pizza` — bumps `0.2.0` → `0.3.0`
**Predecessor specs:** `2026-07-22-pizza-menu-design.md`, `2026-07-24-pizza-v0.2.0-design.md`

## Context

Two independent additions, driven by an online test of v0.2.0:

- **Part A — config self-refresh.** v0.2.0's new menu content (the hotbar item, three catalog
  items) never appeared on the running server: Bukkit's `saveDefaultConfig()` writes the bundled
  default only when `config.yml` is absent, so an existing server keeps its old config and silently
  misses every new default. Pizza is a config-driven plugin, so this affects every future release.
- **Part B — Curse in the menu.** Expose the sibling **TheCurse** plugin (a reversible, timed mob-
  siege survival event) through Pizza: peers can curse a friend *with the friend's consent*, and
  staff can curse or cleanse a player unilaterally.

These are separable and will be separate task groups in the plan, but ship together as v0.3.0.

## Part A — Config self-refresh

### The detection problem

The hard part is telling an **unmodified** config (safe to overwrite with the new default) from a
**customized** one (must never be clobbered). Solution: the plugin carries the SHA-256 of **every
default `config.yml` it has ever shipped** — an embedded resource `config-hashes.txt`, one hash per
line, appended once per release that changes the default.

### Decision (pure, unit-testable)

A `ConfigRefreshDecision` computed from three inputs — the on-disk config bytes, the current bundled
default bytes, and the known-hash set — yields one of:

- **`UP_TO_DATE`** — `sha256(onDisk) == sha256(currentDefault)`. Do nothing.
- **`REFRESH`** — `sha256(onDisk)` is in the known set but is **not** the current default. The config
  is provably an unmodified older default → safe to replace. *This is the case that auto-heals a
  server sitting on the v0.1.0 or v0.2.0 default.*
- **`CUSTOMIZED`** — `sha256(onDisk)` matches nothing in the known set. The admin edited it → never
  overwrite.

### Behaviour (runtime, on enable, before the first parse)

- `REFRESH` → copy the current on-disk file to a timestamped backup (`config.yml.backup-<epoch>`),
  write the bundled default over `config.yml`, log at INFO what happened and where the backup went.
- `CUSTOMIZED` → leave the file untouched, log **once** at INFO: the config looks customized, new
  default features may be missing, and `/pizza config refresh` will reset it (backing the file up
  first). Never nag beyond this one line.
- `UP_TO_DATE` → silent.

### `/pizza config refresh` command

A new `config refresh` subcommand on `/pizza` (permission `pizza.reload`, the existing admin gate):
**unconditionally** back up the current `config.yml` (timestamped), write the bundled default, and
reload — the manual override for a customized server that wants the new defaults. Reports the backup
path in chat.

### Units

- `config/ConfigHashes` — loads the embedded `config-hashes.txt` into a `Set<String>`; exposes the
  current default's hash. Pure apart from reading a bundled resource.
- `config/ConfigRefreshDecision` — the pure `decide(onDiskBytes, currentDefaultBytes, knownHashes)
  → REFRESH | UP_TO_DATE | CUSTOMIZED` function. Unit-tested exhaustively.
- `PizzaPlugin` — wires the decision in on enable (before `parseConfig`), performs the file
  back-up/overwrite for `REFRESH`, and routes `config refresh` from `PizzaCommand`.

### Per-release obligation

Any release that changes `src/main/resources/config.yml` must append the new default's SHA-256 to
`config-hashes.txt`. Documented in the release checklist; a test asserts the *current* shipped
default's hash is present in the file, so forgetting it fails CI.

## Part B — Consent-gated Curse

### What TheCurse is (and why consent fits)

TheCurse applies a **timed, escalating cursed-zombie siege** to an online player — boss bar, glowing
aura, poison if they flee the combat radius, reward chests with an Antidote that ends it. It is
**reversible** (`curse stop`/`curse reset`, the in-game Antidote, and auto-clear on death/quit/
rejoin) and **not** item-destroying — consistent with Pizza's "nothing destructive" line. In
TheCurse's own code, casting is **op-only** (`curse.admin`) and unilateral. Because Pizza dispatches
as **console**, it can trigger a curse for a normal player who has no permission — so **consent is
the safety gate** that makes peer-cursing appropriate.

### Reliable dispatch

Use `curse trigger ZP25 %target%`, not `curse start`: `trigger` bypasses TheCurse's night-only and
cooldown gates, so a consented curse fires regardless of time of day. The mechanic id lives in the
button's command string, so an admin can switch to `CS25P` (explosion variant) or `curse start`
(night-gated) by editing config alone. Cleanse uses `curse stop %target%`.

### Two reused generalizations

1. **Consent on-accept becomes a small sealed set.** Today the consent flow teleports the target on
   Accept. Generalize `PendingInvite`'s outcome into `ConsentAction` = `Travel(world)` (existing,
   unchanged) or `RunCommand(command)` (new). On `ACCEPTED`: `Travel` teleports as before;
   `RunCommand` dispatches the allowlisted command as console with `%target%` = the consenting
   player. Travel's behaviour is byte-for-byte unchanged; this is purely additive.

2. **The online-player picker carries a `consent` flag.** `consent: true` sends the chosen target an
   Accept/Decline ModalForm and runs the command only on Accept (peer curse). `consent: false`
   dispatches immediately (staff). The existing `invite: true` travel button stays as-is.

### Menu configuration (data, once the two generalizations land)

- **Regular players — "Curse a friend":**
  ```yaml
  - label: Curse a friend
    permission: pizza.curse        # new node, default TRUE
    pick: online-players
    consent: true
    command: curse trigger ZP25 %target%
    cooldown: 1h
  ```
  Picks an online player → target sees "Accept the curse from %player%?" → on Accept,
  `curse trigger ZP25 %target%` runs.
- **Staff panel — curse and cleanse (moderation, no consent, no cooldown):**
  ```yaml
  - label: Curse a player
    permission: pizza.staff
    pick: online-players
    consent: false
    command: curse trigger ZP25 %target%
  - label: Cleanse a player
    permission: pizza.staff
    pick: online-players
    consent: false
    command: curse stop %target%
  ```
- Add `curse` to `command-allowlist`.
- New permission `pizza.curse`, default `true`, declared in `plugin.yml`.

### Cooldown — anti-grief (the initiator, on send)

The peer "Curse a friend" cooldown is marked **when the request is sent** (when the initiator picks a
target and Pizza issues the consent prompt), **not** only when the curse lands. This stops a player
rapid-firing curse prompts at others whether or not they accept. If the initiator is still on
cooldown, the pick is refused with the existing cooldown message. Reuses `CooldownService`
(keyed by initiator UUID + button id) and the existing `messages.cooldown`. Staff curse/cleanse carry
no cooldown. Default duration 1h, tunable via the button's `cooldown`.

### Safety rails

- The picker lists **online players only** — TheCurse can't target an offline player anyway.
- `trigger ZP25` is reliable regardless of time; the curse is reversible; **staff can always cleanse**
  a griefed or frightened player. Auto-clear on death/quit/rejoin bounds the worst case.
- Fail-closed allowlist still governs: `curse` unreachable unless listed; a non-allowlisted mechanic
  string is refused at parse like any other command.
- The one rough edge is TheCurse's own daylight/leave-radius **poison penalty**, which can frustrate
  a young player; the staff cleanse and auto-clear-on-death are the mitigations, and the peer curse
  is opt-in by consent.

### Units

- `menu/ConsentAction` — the sealed `Travel`/`RunCommand` type.
- `consent/*` — `PendingInvite` carries a `ConsentAction`; `ConsentService.onAccept` switches on it.
- `config/ConfigParser` — `pick` becomes a **fourth action kind**: the button's exactly-one-action
  rule widens from open/command/invite to **open/command/invite/pick**, and on a `pick` button the
  `command` field is that action's payload (the per-target command), not a standalone command action.
  Validate: a `pick` button needs a `command` whose root is allowlisted, `consent` is a boolean
  (default false), and `cooldown` parses as usual. `pick`'s only supported value is `online-players`.
- `MenuService` — the picker builds per-target buttons carrying the action + consent flag; `consent:
  false` dispatches immediately, `consent: true` routes through `ConsentService`; cooldown marked on
  send for the consent path.

## Testing

**Unit (server-free):**
- `ConfigRefreshDecision.decide` across all three outcomes: current default → `UP_TO_DATE`; a known
  prior default → `REFRESH`; an unknown blob → `CUSTOMIZED`; plus empty/garbage input.
- `ConfigHashes` loads the embedded list; a test asserts the **current** shipped `config.yml`'s
  SHA-256 is present in `config-hashes.txt` (guards the per-release obligation).
- `ConfigParser` accepts the `pick`/`consent`/`command`/`cooldown` button form; refuses a `pick`
  button whose command root is not allowlisted, and one missing a command.
- `ConsentAction` selection: an `ACCEPTED` `RunCommand` dispatches the command with `%target%`; a
  `DECLINED`/`TIMED_OUT`/`CLOSED` runs nothing (extends the existing consent-race tests).
- Shipped-config parse test extended: the curse buttons parse, `curse` is allowlisted, no warnings.

**Runtime / client play-test (owed, now also covers v0.3.0):**
- On upgrade from the v0.2.0 default, the config auto-refreshes (backup written, new buttons appear);
  a hand-edited config is left alone and logs the one-line notice; `/pizza config refresh` resets a
  customized config after backing it up.
- Peer curse: pick a friend → they get the Accept/Decline prompt → Accept triggers the siege; Decline
  runs nothing; the initiator's 1h cooldown blocks an immediate second attempt.
- Staff curse and cleanse fire immediately on a picked target; cleanse ends an active curse.
