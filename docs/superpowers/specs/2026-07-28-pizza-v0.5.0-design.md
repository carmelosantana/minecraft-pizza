# Pizza v0.5.0 — Copper Sword, Shop button, and Java item icons

Date: 2026-07-28
Status: approved
Branch: `feat/pizza-v0.5.0`

## Summary

Three changes to the config-driven menu:

- **A. Copper Sword** in Cool Items — a `player-elevated` button (Copper Kingdom's `give` is self-only).
- **B. Shop** — a new top-level button opening the Farmers Market GUI as the player.
- **C. Java item icons** — the "boring papers" fix: give every shipped button a real Java chest icon
  matching its Bedrock intent, by adding an optional `material` field to a button's image that the
  Java `ChestRenderer` uses and the Bedrock renderer ignores.

Parts A and B are config-only (same proven console/elevated patterns). Part C is a small Java change
(one new record field, a parser line, a `ChestRenderer` preference) plus config icons on every button.
Ships as **v0.5.0**.

A follow-up **background chip** is spun up to improve Copper Kingdom itself (Part A note).

## A. Copper Sword → `catalog`

```yaml
- label: Copper Sword
  run-as: player-elevated
  grant: [copperkingdom.give]
  command: copperkingdom give copper_sword
  material: COPPER_INGOT
```

- `/copperkingdom give <item>` requires a **player sender** and gives to that sender
  (`CopperKingdomCommand.handleGiveCommand` checks `sender instanceof Player`, no player-target arg).
  Pizza's `player-elevated` path runs the command **as the pressing player** with `copperkingdom.give`
  granted through a temporary `PermissionAttachment` removed in a `finally` block — the exact pattern
  the Travel "Go to %world%" button already uses for `worldcrud.teleport`. No `%player%` placeholder is
  needed; the player is the sender and the recipient.
- Allowlist root: `copperkingdom` (the command's first token).
- `copper_sword` is the chosen item (of `copper_sword/axe/pickaxe` + armor); a config swap changes it.

**Follow-up chip (separate session):** improve Copper Kingdom so `give` accepts a player target
(a 4-arg/console form like `gfbread give <type> <player> <n>` and `curse trigger <id> <player>` have),
so Pizza can console-dispatch it like every other catalog item and retire the `player-elevated`
workaround. Pizza needs no change when that lands beyond swapping this button back to `run-as: console`.

## B. Shop → new top-level button in `main`

```yaml
- label: Shop
  image: { type: path, data: 'textures/items/emerald' }
  material: EMERALD
  run-as: player
  command: market
```

- `/market` opens the Farmers Market GUI for the calling player; `farmersmarket.use` is `default: true`.
  `run-as: player` (not console) because it must open a GUI for a real player.
- Allowlist root: **`market`** (the command's first token, not the artifact name `farmersmarket`).
- Placed in the `main` menu after **Travel**, before **Staff**.

## C. Java item icons

### Problem

`ChestRenderer.materialFor` only maps a button to a real icon when `image.type == "material"`; every
shipped button uses a Bedrock `type: path` image (or no image), so Java falls back to `Material.PAPER`
for all of them. A Bedrock button icon is a **texture path**; a Java chest icon is a **Material** —
two representations of the same icon — so a button that wants a correct icon on both platforms must
carry both, which the current single-image model cannot express.

### Change

Add an optional `material` field to the button image so a single button carries both representations:

- **`ButtonImage`** record gains a third component: `record ButtonImage(String type, String data, String material)`.
  `material` is the Bukkit `Material` name the **Java** chest renderer uses as this button's icon;
  it is nullable and independent of `type`/`data`. (Chosen over a new top-level `Button` field because
  `ButtonImage` has a single construction site — `ConfigParser` — whereas `Button` is constructed in
  seven places across main and test code; this keeps `Button`, `MenuService`, and existing tests
  untouched.)
- **`ConfigParser`** reads an optional `material:` key from a button's `image` map into that field.
  A button may also carry `material` with no `type`/`data` (a Java icon and no Bedrock path):
  `image: { material: BREAD }`.
- **`ChestRenderer.materialFor`** resolves the icon in this order: `image.material()` if present and a
  valid `Material`; else the existing `image.type == "material"` path (backward compatible); else
  `Material.PAPER`. An unrecognised `material` name logs a warning and falls back — a bad icon is
  cosmetic, never a render failure (unchanged philosophy).
- **`BedrockRenderer` is unchanged**: it reads only `type`/`data`, never `material`, so the new field
  produces no Bedrock icon and cannot introduce a broken Bedrock texture path.

## Mechanics

- New allowlist roots: `copperkingdom`, `market`.
- `config.yml` edited ⇒ append its new SHA-256 to `config-hashes.txt` (existing lines untouched;
  `ConfigHashesTest.currentDefaultHashIsListed` guards it). Unmodified older configs auto-heal on upgrade.
- `pom.xml` version → `0.5.0`.

## Testing

- **`ButtonImageParseTest`** (new or folded into an existing parser test): `ConfigParser` reads
  `image: { type: path, data: '...', material: DIAMOND }` into `ButtonImage(type, data, material)`,
  and `image: { material: BREAD }` into `ButtonImage(null, null, "BREAD")`.
- **`ChestRenderer`** unit test: a button whose `image.material()` is `BREAD` renders an `ItemStack`
  of `Material.BREAD`; a button with an unrecognised `material` and no other icon falls back to
  `PAPER` without throwing; a button with a Bedrock-only `type: path` image (no `material`) still
  falls back to `PAPER` (documents that a path alone does not produce a Java icon).
- **`ShippedConfigTest`** extended: catalog contains `copperkingdom give copper_sword`; some menu
  contains a button dispatching `market`; allowlist contains `copperkingdom` and `market`; the
  shipped Cool Items button carries `image.material() == "DIAMOND"` (proves icons are wired end to end);
  `shippedConfigParsesWithoutWarnings` stays green.
- Full `mvn clean verify` green.

## Non-goals

- **Menu polish** (styled names, lore, glass-pane borders) — deferred; icons only this cycle
  (user decision).
- **Curse / GeoBrot fractal travel** — still parked.
